# Лог разработки: SD-карта + WAV-рекордер

## 2026-06-01 — Старт. Изучение железа и архитектуры

Открыл задачу. На фото — стандартный модуль MicroSD Card Adapter с чипом-буфером уровней
(скорее всего TXS0108 или аналог — 3.3В логика на SPI). Карта — Smartbuy 32GB SDHC Class 10.
Всё это должно подключиться к Pico по SPI.

Первый вопрос, который встал сразу: SD-карта изнутри — NAND flash, со всеми вытекающими
(стирание секторами, write leveling). Но! Снаружи всё это спрятано за контроллером внутри
карты. По SPI мы общаемся с этим контроллером, а не с NAND напрямую. Минимальная единица
операции — **512-байтный блок**. Записывать можно прямо поверх существующих данных,
стирание контроллер делает сам. Для нас это чистый блочный интерфейс.

Посмотрел предыдущие проекты репозитория. Паттерн везде одинаковый:
- `stdio-task` — неблокирующий ввод по USB CDC
- `led-task` — мигание встроенного светодиода
- `protocol-task` — диспетчер команд из общей библиотеки `libs/protocol`
- HAL-драйвер периферии в `libs/` с чистым интерфейсом через структуру с указателями на функции

Решил делать SD-драйвер по той же схеме: `libs/sd-driver` с HAL-структурой, которая
принимает `spi_transfer`, `cs_set`, `delay_ms`. Так драйвер можно портировать на любой МК.

Выбрал пины SPI1: GP10 (SCK), GP11 (MOSI), GP12 (MISO), GP13 (CS). Не пересекаются с
дисплеем из прошлого проекта (там был SPI0 на GP4-7).

Написал архитектуру в PLAN.md, написал заметку про физику SD-карт, приступил к коду.

### Ключевое решение по инициализации SD по SPI

Протокол SD/SPI — классика, но с нюансами:
1. При подаче питания нужно послать ≥74 тактовых импульса с CS=HIGH (иначе карта не выйдет
   из native SD mode в SPI mode).
2. CMD0 — программный сброс. Карта должна ответить 0x01 (idle state).
3. CMD8 с паттерном 0xAA — проверка уровня питания и определение версии (v2 = SDHC capable).
4. ACMD41 (это CMD55 + CMD41) с флагом HCS=1 — карта инициализирует контроллер flash. Нужно
   повторять в цикле пока не ответит 0x00 (ready). Таймаут ~2 секунды.
5. CMD58 — читаем OCR. Бит CCS (bit30) = 1 → SDHC (блочная адресация). = 0 → SDSC
   (байтовая адресация, адрес = block_num * 512).

Это важно потому что у нас SDHC 32GB — нужна именно блочная адресация.

Тактовая частота: при инициализации ≤400 kHz обязательно. После успешного CMD58 можно
поднять до 25 MHz (максимум для SPI mode) или выше если карта поддерживает. Для надёжности
буду ставить 10 MHz на рабочий режим.

### Тест-паттерн

Для низкоуровневого теста буду писать в блок 2048 (1 MB offset) — это заведомо вне
загрузочного сектора и FAT-таблиц отформатированной карты. Паттерн: `buf[i] = i & 0xFF`,
первые 4 байта — little-endian номер блока. По этому паттерну легко видеть что именно
прочиталось если есть расхождение.

### Что реализовано

- `libs/sd-driver/` — HAL-драйвер: init, read_block, write_block
- `06-sd/sd-task/` — обёртка с командами sd_info, sd_test, sd_write_block, sd_read_block
- `06-sd/main.c` — точка входа, полный API с protocol-task
- Весь build system (CMakeLists.txt, linker script, pico_sdk_import)

## 2026-06-02 — Проблема с питанием + диагностика init

### ⚠️ ВНИМАНИЕ: модуль нельзя питать от 3.3В пина Pico

Измерение мультиметром показало критическое падение напряжения:

| Напряжение на VCC модуля | Напряжение на питании SD-карты |
|--------------------------|-------------------------------|
| 3.3В (от Pico 3V3)       | **2.2В** — карта не инициализируется |
| 5.0В (от VBUS)           | **3.3В** — норма |

Причина: на модуле стоит **AMS1117-3.3** — линейный стабилизатор, которому нужно минимум
~1В разницы (dropout voltage). При входе 3.3В он выдаёт 2.2В вместо 3.3В. SD-карта при
2.2В либо вообще не включается, либо ведёт себя непредсказуемо.

**Правило на будущее: MicroSD Card Adapter такого типа всегда питать от 5В (VBUS, pin 40 Pico).**

Пины данных (MOSI/MISO/SCK/CS) при этом остаются на 3.3В — внутри модуля AMS1117 снижает
питание до 3.3В, и данные идут на 3.3В стороне. Pico GPIO в безопасности.

### Пошаговая диагностика: ACMD41 зависает навсегда

Питание исправлено (5В → 3.3В через AMS1117), но ACMD41 всё равно возвращает 0x01
бесконечно — даже за 5 секунд. За это время было проверено несколько гипотез:

**Гипотеза 1: CS нужно держать LOW между CMD55 и CMD41.**
Некоторые источники утверждают, что карта «забывает» APP_CMD при подъёме CS. Проверили —
не помогло. Карта и так принимала ACMD41 правильно (0x01, а не 0x05).

**Гипотеза 2: нужен байт 0xFF перед каждой командой.**
Добавили «пробуждающий» байт в начало `sd_send_cmd` — стандартная практика из FatFS.
Не изменило картину.

**Гипотеза 3: нужен более длинный таймаут или медленная частота.**
Увеличили таймаут до 30 сек, снизили SPI до 100 кГц — без эффекта.

Добавили команду `sd_debug` — шлёт сырые команды и дампит 10 байт ответа. Это позволило
поставить точный диагноз:

```
CMD41 (no CMD55, expect 0x05): recv: FF 05 ...   ← правильно, CMD55 работает
CMD55:                          recv: FF 01 ...   ← принято
CMD41 (after CMD55):            recv: FF 01 ...   ← ACMD41 понимается, но init не завершается
CMD58 OCR:                      recv: FF 01 00 FF 80 00 ...
```

OCR = `0x00FF8000` → бит 31 = 0 (power up not complete). Это ожидаемо ДО завершения ACMD41.
Ключевой вывод: **протокол реализован верно**. Карта корректно различает CMD41 и ACMD41,
принимает все команды — просто никогда не завершает internal power-up. Проблема аппаратная.

### Причина найдена: бракованная карта

Попробовали вторую microSD (тоже Smartbuy, другой экземпляр). Результат:

```
[sd] ACMD41 t=0ms: CMD55 R1=0x01, CMD41 R1=0x01
[sd] ACMD41 result: R1=0x00 after 10ms
[sd] CMD58 R1=0x00 OCR=C0 FF 80 00 → SDHC/SDXC
[sd] init complete: SDHC/SDXC
```

Первая карта не завершала internal power-up ни за 5, ни за 30 секунд — классический
симптом брака NAND-контроллера. Вторая — инициализировалась за 10 мс.

**Урок:** при проблемах с ACMD41 в первую очередь пробовать другую карту.

### Этап 1 завершён — низкоуровневый тест пройден

```
Writing pattern to block 2048 ... OK
Reading block 2048 ... OK
Verify: PASS — all 512 bytes match
```

Запись и чтение 512-байтных блоков по SPI работают. После подтверждения параметры init
возвращены к каноничным (400 кГц, таймаут 2 сек, интервал 10 мс) — карта инициализируется
за 10 мс при любых значениях, а длинный таймаут лишь затягивает диагностику при сбое.

Итоговый API этапа 1:
- `sd_info` — verbose-инициализация с выводом каждого шага
- `sd_debug` — сырой дамп SPI-ответов: CMD0/8/58, CMD41 без CMD55, ACMD41
- `sd_test [block]` — запись паттерна, чтение, сравнение
- `sd_write_block <n>` / `sd_read_block <n>` — ручная работа с конкретным блоком

## 2026-06-02 — Этап 2: FatFS + генерация WAV-файлов

### Архитектура FatFS-слоя

Раз физическая запись работает, можно добавить файловую систему. Схема слоёв:
```
wav_sine / sd_ls / sd_download  ← команды пользователя
         ↓
       FatFS                    ← файловая система (ff.c)
         ↓
     diskio.c                   ← мост: FatFS ↔ sd_driver
         ↓
     sd-driver                  ← блочный SPI-драйвер (без изменений)
```

FatFS уже лежит в pico-sdk по пути `lib/tinyusb/lib/fatfs/source/` — нет смысла
скачивать отдельно. Просто ссылаемся на эти файлы из `libs/fatfs/CMakeLists.txt`.

Один нюанс: `ff.c` при включении `"ffconf.h"` ищет файл в своей же директории
(правило GCC для кавычечных include). Кастомный `ffconf.h` в `libs/fatfs/` игнорируется.
Решение: использовать bundled конфиг (он уже с LFN), и добавить `ffunicode.c` в сборку.

### diskio.c — мост к sd-driver

`diskio.c` — стандартный интерфейс FatFS для работы с диском. Реализован через
два новых метода `sd_task_ensure_init()` и `sd_task_card()`, которые экспортируют
из `sd-task.c` уже инициализированный объект `sd_t`.

Схема: FatFS вызывает `disk_initialize()` → `sd_task_ensure_init()` → `sd_init()`.
После этого `disk_read()`/`disk_write()` переадресуют в `sd_read_block()`/`sd_write_block()`.

### WAV-файлы: формат и генерация

WAV = RIFF-контейнер с PCM аудиоданными. Заголовок 44 байта, потом сырые int16_t.
Параметры: 44100 Гц, 16-бит, моно. 3 секунды = 44100 × 3 × 2 = 264 600 байт.

Синус генерируется chunk'ами по 256 семплов (512 байт = один SD-блок):
```c
chunk[j] = (int16_t)(28000 * sinf(2π * freq * (i+j) / 44100));
```
Pico RP2040 имеет аппаратный FPU — `sinf()` выполняется быстро.

Нумерация файлов: сканируем каталог, берём максимальный N из `NNN.WAV`,
следующий = N+1. Первый файл = `001.WAV`.

### sd_download: base64-протокол

Бинарная передача по serial требует отключать CR/LF-трансляцию stdio. Проще
обойти это: кодировать файл в base64 (ASCII, 33% overhead) и передавать как текст.

Протокол:
```
DOWNLOAD:001.WAV:264644
SGVsbG8gV29ybGQ...  ← строки по 64 base64-символа
...
DONE
```

Python-скрипт `sd_tool.py` декодирует base64 и сохраняет файл в
`downloads/<дата-время>/` с оригинальным именем.

### Отладка: три последовательных бага

#### Баг 1 — mount error: 1 (FR_DISK_ERR)

Первый запуск `wav_sine` сразу после прошивки дал `mount error: 1`. Добавили вывод
в `diskio.c` и обнаружили: `disk_read sector 8192 failed: timeout`.

Причина: `sd_read_block` ждала токен данных `0xFE` в цикле `TIMEOUT_READ_MS * 10 = 2000`
итераций. При 10 МГц SPI каждая итерация = 0.8 мкс → итого **1.6 мс** вместо 200 мс.
Сектор 0 (MBR) карта отдавала быстро, сектор 8192 (начало FAT-раздела) — нет.

Исправление: цикл опроса переписан с `hal->delay_ms(1)` — 1000 байтовых опросов,
потом 1 мс задержка, до `TIMEOUT_READ_MS` миллисекунд. Корректно при любой частоте SPI.

#### Баг 2 — mount error: 13 (FR_NO_FILESYSTEM)

После исправления таймаута чтения монтирование дошло дальше, но вернуло ошибку 13.
Исправление: добавили явный `sd_task_ensure_init()` перед `f_mount` в каждой команде —
это позволило увидеть вывод `[diskio]` при ошибках. Сама ошибка 13 была артефактом
предыдущего бага: при старом таймауте FatFS не мог прочитать нужные секторы и
считал файловую систему отсутствующей.

#### Баг 3 — write error at sample 1792 (timeout на disk_write)

Монтирование прошло, файл создался, заголовок WAV записан, но при записи первых
аудио-данных: `disk_write sector 16305 failed: timeout`.

Причина: запись приняла данные (data response token = 0x05 OK), но карта ушла в
состояние «занята» на >500 мс. Это граница NAND-блока: SD-контроллер обязан стереть
блок перед повторной записью, стирание занимает до 2–3 секунд на дешёвых картах
(Smartbuy SDHC 32 GB).

В Stage 1 это не проявлялось — тестовый сектор 2048 оказался в чистой области.
FatFS пишет последовательно и неизбежно натыкается на блоки с «грязными» данными.

Исправление: `TIMEOUT_WRITE_MS` увеличен с 500 до 10000 мс.

### Итог этапа 2 — всё работает ✅

Все три команды проверены на железе:
- `wav_sine 440 3` → создаёт 003.WAV, 264 644 байта, прогресс 10%..90%..OK
- `sd_ls` → выводит список файлов с размерами
- `sd_download 003.WAV` → передаёт файл base64-строками, заканчивает `DONE`

Файлы воспроизводятся стандартными плеерами после вставки карты в компьютер.

Python-скрипт `sd_tool.py`:
```
python sd_tool.py ls
python sd_tool.py wav-sine 440 3
python sd_tool.py download 001.WAV
python sd_tool.py download-all
```

## 2026-06-02 — Этап 3: запись с АЦП

### Архитектура

Ключевой вопрос этапа: как не потерять семплы при записи на SD? SD-карта может уйти в
паузу на 1–3 секунды при стирании NAND-блока. За это время на 8 кГц накапливается
24 000 семплов — FIFO глубиной 8 не справится.

Решение: **запись сначала в RAM через DMA, потом на SD**.
- DMA захватывает ADC FIFO в буфер `rec_buf[80000]` (160 KB в BSS).
- DMA работает автономно — не зависит от скорости SD.
- После `dma_channel_wait_for_finish_blocking` — данные в RAM, затем обычная запись WAV.

Почему 8 кГц, а не 44100:
- 10 сек при 44100 Гц = 882 000 семплов × 2 байта = 1.7 MB — не влезает в 256 KB RAM.
- 8 кГц хватает для голоса, генератора сигналов, датчиков.
- Максимум записи: 10 сек (80 KB семплов → 160 KB буфер).

### Конвертация ADC → PCM

RP2040 ADC: 12-bit, диапазон 0–4095. WAV PCM: int16_t, диапазон −32768..32767.
Формула: `sample = (raw − 2048) << 4`. Центрирует сигнал вокруг нуля,
растягивает 12 бит до 16 бит без потери линейности.

### Делитель тактовой АЦП

`adc_set_clkdiv(5999.0f)` → 48 МГц / 6000 = ровно 8000 Гц.
Каждый цикл АЦП = 96 тактов (fixed в RP2040), так что дробные делители
не нужны для стандартных частот.

### Файловое пространство

`rec_start` использует ту же функцию `next_wav_name()` — нумерация продолжает
общий пул с `wav_sine`. Файлы `001.WAV`, `002.WAV` ... без разграничения типов.
Это упрощает `sd_download` и `sd_ls` — они работают со всеми WAV одинаково.

### Итог первой версии этапа 3 — запись работает, лимит 10 сек ✅

Прошивка: `rec_start <seconds>` (1..10). DMA захватывает все семплы в RAM,
затем записывает на SD. Семплы не теряются. Ограничение: 10 сек × 8 кГц × 2 байта
= 160 KB RAM — на грани допустимого при 256 KB SRAM.

## 2026-06-02 — Этап 3, часть 2: двойная буферизация и второе ядро

### Задача: снять ограничение по времени

Пользователь задал вопрос: «Можно ли писать дольше 10 секунд?»

Первый вариант с RAM-буфером уперался в физику: 256 KB SRAM на RP2040.
При 8 кГц максимум ≈ 15 сек, комфортно ≈ 10 сек. Увеличить частоту или время
не получится без смены архитектуры.

### Двойная буферизация — снятие лимита по RAM

Ключевое наблюдение: нам не нужно хранить весь файл в RAM. Нужно только,
чтобы DMA успел наполнить один буфер, пока мы записываем другой.

```
Буфер A: [████████████] ← DMA пишет (4 сек)
Буфер B: [████████████] → SD-карта читает (обычно < 0.5 сек, max ~3 сек)
```

Условие: DMA-время > время записи на SD.
- Буфер 32 000 семплов × 8 кГц = **4 секунды** DMA.
- Запись 64 KB на SD: обычно < 0.5 сек, при NAND-стирании до **~3 сек**.
- Запас: 4 сек > 3 сек → семплы **не теряются**.

Итог: ограничение по времени снято полностью. Два буфера = 128 KB RAM.
Это даже меньше, чем первый вариант (160 KB). Максимум команды — 1 час.

Цикл записи:
```
захват buf[0]                        ← первый чанк, просто ждём DMA
старт DMA на buf[1] / запись buf[0]  ← параллельно
ждём DMA → старт DMA на buf[0] / запись buf[1]
...
```

### Задача: rec_stop в любой момент

После двойной буферизации пришёл следующий вопрос: «Можем ли мы в процессе
записи вызвать rec_stop?»

С блокирующим `dma_channel_wait_for_finish_blocking` на Core 0 это невозможно:
командный цикл не получает управления во время записи. Нужно второе ядро.

### Первое использование Core 1 — правильный момент

RP2040 имеет два ядра, но до этого момента всё работало на Core 0.
Это первый раз, когда задача потребовала Core 1 — и это именно тот случай,
для которого двухъядерность создана:

> **Две параллельные задачи, которые нельзя прерывать:** непрерывный захват
> АЦП (нельзя прерывать — потеряем семплы) + обработка команд от пользователя
> (нельзя блокировать — нужно принять rec_stop).

Распределение:
```
Core 0: stdio → protocol_task → led_task    ← командный цикл, как всегда
Core 1: DMA → запись чанков → f_close       ← непрерывная запись
```

Синхронизация — два `volatile` флага:
```c
volatile bool rec_stop_flag;  /* Core 0 выставляет → Core 1 читает */
volatile bool rec_running;    /* Core 1 выставляет/сбрасывает      */
```

`volatile` гарантирует, что компилятор не закеширует значение в регистре.
Атомарность записи одного байта/слова на ARM Cortex-M0+ гарантирована
аппаратно — мьютекс для флага не нужен.

Запуск и остановка Core 1:
```c
/* rec_start: */
multicore_reset_core1();          /* сброс если уже запускался */
multicore_launch_core1(core1_recording);  /* Core 1 стартует */

/* rec_stop: */
rec_stop_flag = true;             /* Core 1 увидит на следующей итерации */
```

Core 1 проверяет флаг между чанками — т.е. максимальная задержка остановки
равна времени DMA одного чанка (4 сек) + времени записи чанка на SD (~3 сек).
Это приемлемо.

### Исправление WAV-заголовка при досрочной остановке

WAV требует в заголовке размер данных. При `rec_start` мы не знаем, когда
придёт `rec_stop`. Решение: записать заголовок с нулями, а после остановки
исправить через `f_lseek`:

```c
/* При открытии файла: */
wav_write_header_placeholder(&fil);   /* RIFF size = 0, data size = 0 */

/* После последнего f_write: */
f_lseek(&fil, 4);                     /* поле RIFF size */
write_u32le(&fil, 36 + data_size);

f_lseek(&fil, 40);                    /* поле data size */
write_u32le(&fil, data_size);
```

FAT32 поддерживает `f_lseek` на открытом файле. Файл корректен в любых плеерах.

### Итог этапа 3 — всё работает ✅

Проверено на железе:
- `rec_start` — запись стартует немедленно, Core 1 захватывает АЦП
- `rec_start 30` — максимум 30 сек, `rec_stop` останавливает раньше
- `rec_stop` — Core 1 дописывает последний чанк, исправляет заголовок, закрывает файл
- `sd_ls` / `sd_download` во время записи → `busy: recording in progress`
- WAV-файлы открываются в плеерах, сигнал с генератора виден на осциллограмме плеера

Python-скрипт:
```
python sd_tool.py record 5          # 5 сек, блокирующий
python sd_tool.py record-start      # старт без лимита
python sd_tool.py record-stop       # стоп + скачать файл
```
