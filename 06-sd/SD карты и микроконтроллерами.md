# SD-карты и микроконтроллеры

## Что внутри SD-карты

SD-карта — это NAND flash + встроенный контроллер. NAND flash имеет несколько важных
ограничений на уровне физики:

- **Минимальная единица записи — страница** (~512 байт или кратно).
- **Минимальная единица стирания — блок** (несколько тысяч страниц).
- **Нельзя перезаписать поверх без предварительного стирания** — у NAND ячейки
  можно только программировать в 0, но не в 1. Чтобы вернуть 1, нужно стереть весь блок.
- **Ограниченное количество циклов P/E** (~1000–10000 для MLC NAND).

Контроллер SD-карты скрывает всю эту физику и предоставляет снаружи **блочный интерфейс**:
- Блок = 512 байт.
- Можно читать и писать любой блок — контроллер сам выполняет erase-before-write, FTL
  (Flash Translation Layer) и wear leveling.
- Для МК это выглядит как жёсткий диск: адресуемое хранилище из 512-байтных секторов.

**Вывод: по SPI мы просто читаем/пишем 512-байтные блоки по номеру. Всё остальное — за нас.**

## Интерфейсы SD-карт

SD-карты физически поддерживают два интерфейса:
- **SD (native)** — 4-битная шина, высокая скорость (до 100+ MB/s у UHS).
- **SPI** — стандартный 4-проводной SPI, значительно медленнее, но проще.

Для МК без SDIO-контроллера (например Pico RP2040) используем SPI. Максимальная скорость
в SPI mode — 25 MHz, что даёт ~3 MB/s. Для WAV-записи (16 кГц × 2 байта = 32 кБ/с) это
более чем достаточно.

## Типы SD-карт и адресация

| Тип   | Ёмкость     | Адресация в SPI      |
|-------|-------------|----------------------|
| SDSC  | ≤2 GB       | Байтовая (block × 512) |
| SDHC  | 2–32 GB     | Блочная (номер блока)  |
| SDXC  | 32–2000 GB  | Блочная              |

Наша карта: Smartbuy 32 GB → **SDHC**, блочная адресация.

## Инициализация SD по SPI: пошагово

```
Power up → ждём >1 мс

1. CS=HIGH, отправить 10 байт 0xFF (80 тактов) — карта переходит в SPI mode

2. CS=LOW
   CMD0 (GO_IDLE_STATE, arg=0, CRC=0x95)
   Ждём R1 = 0x01 (idle) — это норма при инициализации

3. CMD8 (SEND_IF_COND, arg=0x000001AA, CRC=0x87)
   Ответ R1=0x01 + 4 байта → последние 2 должны быть 0x01, 0xAA
   Если R1=0x05 (illegal cmd) — карта SDSC v1 (сейчас таких почти нет)

4. ACMD41 = CMD55 + CMD41 (arg=0x40000000, HCS bit set)
   Повторяем до R1=0x00, таймаут ~2 сек
   R1=0x00 означает: карта инициализирована и готова

5. CMD58 (READ_OCR, arg=0)
   Ответ: R1=0x00 + 4 байта OCR
   Бит 30 (CCS) = 1 → SDHC/SDXC, блочная адресация
   Бит 30 (CCS) = 0 → SDSC, байтовая адресация

6. Поднять частоту SPI до рабочей (≤25 MHz)
   При SDSC отправить CMD16 (SET_BLOCKLEN, arg=512)
```

## Чтение блока (CMD17)

```
CS=LOW
CMD17 (arg = block_num для SDHC, block_num*512 для SDSC)
Ждём R1 = 0x00
Ждём токен данных 0xFE (посылаем 0xFF, читаем пока не придёт 0xFE)
Читаем 512 байт данных
Читаем 2 байта CRC (можно игнорировать)
Отправляем 1 байт 0xFF (card release)
CS=HIGH
```

## Запись блока (CMD24)

```
CS=LOW
CMD24 (arg = block_num)
Ждём R1 = 0x00
Отправляем 1 байт 0xFF (пауза)
Отправляем токен 0xFE (начало данных)
Отправляем 512 байт данных
Отправляем 2 байта CRC-заглушки (0xFF 0xFF)
Читаем data response token: нижние 4 бита = 0x05 → данные приняты
Посылаем 0xFF пока карта занята (получаем 0x00 → ждём, не 0x00 → готова)
Отправляем 1 байт 0xFF
CS=HIGH
```

## ⚠️ Питание модуля MicroSD Card Adapter

Большинство готовых модулей (с разъёмом под microSD на плате) содержат **AMS1117-3.3** —
линейный стабилизатор с dropout ~1.1–1.3В. Это значит:

| Вход VCC | Выход на карту | Результат |
|----------|---------------|-----------|
| 3.3В     | ~2.2В         | ❌ карта не инициализируется |
| 5В       | 3.3В          | ✅ норма |

**Правило: такие модули питать только от 5В (VBUS, pin 40 Pico).**

Линии данных (MOSI/MISO/SCK/CS) при этом безопасны — AMS1117 переводит питание в 3.3В,
данные идут на 3.3В стороне, GPIO Pico не повреждаются.

Проверено измерением: при 3.3В на VCC карта получает 2.2В и зависает на ACMD41.

## Как читать OCR (регистр CMD58)

CMD58 возвращает R1 (1 байт) + OCR (4 байта, MSB первым):

```
recv: FF  R1  OCR[31:24]  OCR[23:16]  OCR[15:8]  OCR[7:0]
      FF  01  00          FF          80          00
```

Пример: OCR = `0x00FF8000`
- Бит 31 = 0 → **карта ещё не завершила power-up** (норма ДО успешного ACMD41)
- Бит 30 = 0 → CCS (Card Capacity Status) — не определён до завершения init
- Биты 23:15 = `0x1FF` → все напряжения 2.7–3.6В поддерживаются

После успешного ACMD41 (R1=0x00), CMD58 возвращает:
```
recv: FF  00  C0  FF  80  00
```
OCR = `0xC0FF8000`:
- Бит 31 = 1 → power up complete ✓
- Бит 30 = 1 → CCS = 1 → **SDHC/SDXC** (блочная адресация) ✓

## Диагностика SPI-протокола командой sd_debug

Вместо осциллографа можно проверить протокол прямо из прошивки. Команда `sd_debug`
шлёт ключевые команды и дампит 10 сырых байт ответа:

```
CMD41 (no CMD55, expect 0x05): recv: FF 05 ...
```
- `0x05` = illegal command → CMD55 работает корректно, CMD41 без него не принимается ✓
- `0x01` вместо `0x05` → карта вообще не различает ACMD (очень редкая проблема)
- `0xFF` → нет контакта по MISO

```
CMD55: recv: FF 01 ...
CMD41 (after CMD55): recv: FF 01 ...
```
- `0x01` → карта понимает ACMD41, ещё инициализируется (норма в первые итерации)
- `0x00` → инициализация завершена ✓
- `0x05` → CMD55 не был принят как APP_CMD (протокольная ошибка)

## Советы по отладке

- **Если CMD0 не отвечает**: убедись что послал ≥74 клока с CS=HIGH перед первой командой,
  и что питание карты ≥2.7В (проверь мультиметром).
- **Если ACMD41 зависает навсегда** (0x01 бесконечно, даже за 5+ сек):
  1. Сначала попробуй **другую карту** — первая может быть бракованной.
  2. Проверь питание — модуль с AMS1117 требует 5В на входе.
  3. Используй `sd_debug` чтобы убедиться что CMD41 без CMD55 = 0x05.
     Если протокол правильный, а карта всё равно не init — она неисправна.
- **Если данные читаются как 0xFF**: MISO не подключён или перепутан с MOSI.
- **Проблемы на высокой частоте**: сначала проверь на 400 кГц (max при init по спеку).
- **Некорректные данные от FAT**: при тестах записывай в блоки 2048+, чтобы не затереть
  MBR/FAT и не сломать видимость файлов с компьютера.

## ⚠️ Таймауты SPI и NAND-стирание

### Таймаут ожидания токена данных (read)

После CMD17 карта возвращает токен `0xFE` перед 512 байтами данных. Спецификация
допускает задержку до **100 мс** между командой и началом данных.

**Ошибка:** цикл `for (i < TIMEOUT * 10) { spi_byte(); }` даёт время, зависящее
от частоты SPI. При 10 МГц: `200 * 10 * 0.8 мкс = 1.6 мс` — в 60 раз меньше нужного.
Первый сектор карты (MBR, сектор 0) успевает, а сектор 8192 (начало FAT-раздела) — нет.

**Правило:** таймаут ожидания токена должен использовать реальное время, а не счётчик
байтов. Правильный шаблон на HAL:
```c
for (uint32_t t = 0; t < TIMEOUT_MS && !found; t++) {
    for (int j = 0; j < 1000; j++) {         // ~1ms при 10 МГц
        token = spi_byte(sd, 0xFF);
        if (token != 0xFF) { found = true; break; }
    }
    if (!found) hal->delay_ms(1);
}
```

### Таймаут ожидания готовности после записи (write)

После записи блока карта удерживает MISO=0 (busy) пока программирует NAND.
Спецификация: **250 мс** типично, до **500 мс** максимум для одного блока.

Но: первая запись в новый NAND-блок стирания требует **erase** — это 1–3 секунды
на дешёвых картах (Smartbuy SDHC 32 GB). Типичный размер блока стирания: 4 MB
(8192 секторов). При последовательной записи файлов это происходит каждые ~4 МБ.

**Правило:** `TIMEOUT_WRITE_MS` должен покрывать erase — минимум **5000 мс**, лучше
**10000 мс** для надёжности. Это не влияет на нормальную скорость записи: большинство
секторов программируются за <100 мс, пауза возникает только на границах блока стирания.

Пример: файл 001.WAV (265 KB) может занять несколько секунд из-за одной такой паузы,
а 002.WAV (тот же объём) запишется за доли секунды — блок уже стёрт.

## Использование FatFS (этап 2)

Elm-Chan FatFS — стандартная де-факто библиотека файловой системы для МК. Требует реализации
`disk_read`, `disk_write`, `disk_status`, `disk_initialize` — всё это тонкая обёртка над
нашим `sd_read_block` / `sd_write_block`.

Когда файловая система поднята, нет нужды думать о FAT, кластерах, именах файлов — всё через
стандартный API: `f_open`, `f_write`, `f_close`.

## Запись АЦП в реальном времени

### Постановка задачи

Хотим захватывать аналоговый сигнал с GPIO26 (ADC0) и писать его в WAV-файл
на SD-карту. На первый взгляд всё просто: читаем АЦП → пишем на SD → повторяем.

Проблема возникает сразу, как только вспоминаем про NAND:

```
SD-карта уходит «в раздумья» на 1–3 секунды при стирании NAND-блока.
АЦП продолжает семплировать — его некуда складывать.
FIFO АЦП на RP2040 = 8 семплов.
При 8 кГц → 8 семплов = 1 мс.
```

Через 1 мс FIFO переполнится, данные пропадут. В записи появится пропасть.

### Версия 1: захват в RAM, запись потом

Самое простое решение: сначала захватить всё в RAM через DMA, потом записать.

```
adc → DMA → rec_buf[80000]   ← 160 KB, вся запись в RAM
↓
всё записано → пишем WAV на SD
```

DMA работает полностью автономно — пока идёт захват, процессор свободен.
После `dma_channel_wait_for_finish_blocking` данные уже в памяти, SD-пауза
уже не страшна.

**Ограничение:** размер буфера ограничен SRAM.
При 8 кГц × 2 байта = 16 KB/сек → в 256 KB RAM влезает ~10 секунд.
Это уже реализовано и работает.

```c
static uint16_t rec_buf[80000]; /* 160 KB в BSS */

dma_channel_configure(dma_chan, &cfg,
    rec_buf, &adc_hw->fifo, num_samples, true);
adc_run(true);
dma_channel_wait_for_finish_blocking(dma_chan); /* ждём */
adc_run(false);
/* теперь пишем WAV на SD — сколько угодно времени */
```

Это правильная архитектура для коротких записей. Когда нужно больше — переходим
к версии 2.

### Версия 2: двойная буферизация

Идея: не хранить весь файл в RAM — держать только два буфера, попеременно:
один заполняет DMA, другой в это время пишется на SD.

```
Итерация 1:  DMA → buf[0]  (захват, 4 сек)
Итерация 2:  DMA → buf[1]  ‖  SD ← buf[0]   ← параллельно
Итерация 3:  DMA → buf[0]  ‖  SD ← buf[1]
...
```

**Условие надёжности:** DMA-время одного буфера > время записи на SD.

| Что | Время |
|-----|-------|
| DMA 32 000 семплов при 8 кГц | **4 секунды** |
| Запись 64 KB на SD (обычно) | < 0.5 сек |
| Запись 64 KB на SD (NAND-стирание) | до ~3 сек |

4 сек > 3 сек — буфер всегда успевает записаться до следующей итерации.

Ограничение по времени снято: RAM-буфер теперь фиксированные **128 KB** (два буфера
по 64 KB), а запись может идти хоть час.

```c
static uint16_t adc_buf[2][32000]; /* 128 KB: два буфера */

/* Захватываем первый чанк */
launch_dma(adc_buf[0], CHUNK);
wait_dma();

/* Основной цикл: немедленно запускаем следующий DMA, пишем предыдущий */
while (!stop) {
    launch_dma(adc_buf[next], CHUNK);    /* ← DMA стартует немедленно */
    write_chunk_to_sd(adc_buf[cur]);     /* ← пишем параллельно с DMA */
    wait_dma();                          /* ← ждём конца DMA */
    swap(cur, next);
}
```

Порядок важен: `launch_dma` должен быть **до** `write_chunk_to_sd`. Иначе
пока мы пишем на SD, никакой DMA не запущен и семплы теряются.

## Второе ядро: когда оно действительно нужно

### Архитектура RP2040

RP2040 имеет два ядра Cortex-M0+. Они разделяют:
- всю SRAM (256 KB)
- все периферийные устройства (SPI, I2C, ADC, DMA...)
- все GPIO

Каждое ядро имеет собственный:
- счётчик команд (PC) и стек
- регистровый файл

По умолчанию после сброса работает только Core 0. Core 1 спит до явного запуска.

### Проблема: rec_stop во время записи

После версии 2 (двойная буферизация) появился вопрос:
«Можно ли отправить `rec_stop` пока идёт запись?»

С текущей архитектурой — нет. `dma_channel_wait_for_finish_blocking` держит Core 0
заблокированным на 4 секунды (время DMA-чанка). Командный цикл не получает управления.
Любая команда, включая `rec_stop`, будет проигнорирована до конца чанка.

Это не баг — это фундаментальное ограничение однопоточного подхода.

### Когда нужно второе ядро

Второе ядро нужно, когда есть **две независимые задачи**, обе из которых нельзя
прерывать и нельзя ждать:

> **Core 0:** обработка команд (нельзя блокировать — нужно принять `rec_stop`)
> **Core 1:** непрерывный захват АЦП (нельзя прерывать — потеряем семплы)

Это именно тот случай. Не «хочется», а «нельзя иначе».

Добавить прерывание? DMA-complete ISR завершит чанк, но во время ISR командный
цикл всё равно не работает — они оба на Core 0.

Добавить кооперативную многозадачность? Тогда нужно разбить `wait_dma()` на
неблокирующий опрос, и командный цикл сможет крутиться между проверками. Это
работает, но усложняет код и создаёт задержки обработки команд до 4 сек.

Второе ядро — чистое и прямолинейное решение.

### Запуск Core 1

```c
void core1_recording(void)
{
    /* Эта функция выполняется на Core 1. */
    /* ... захват DMA + запись WAV ... */
    rec_running = false;
}

/* На Core 0, в rec_start_callback: */
multicore_reset_core1();                  /* сброс если уже запускался */
multicore_launch_core1(core1_recording);  /* Core 1 стартует немедленно */
/* Core 0 возвращается в командный цикл — не ждёт! */
```

`multicore_launch_core1` возвращается сразу. Core 0 продолжает работу.
Core 1 начинает `core1_recording` независимо.

### Синхронизация через volatile-флаги

Два ядра разделяют SRAM, но у каждого есть кеш регистров. Компилятор может
оптимизировать чтение переменной: прочитать один раз в регистр и больше в память
не лезть. Тогда Core 1 никогда не увидит изменение, сделанное Core 0.

Ключевое слово `volatile` запрещает эту оптимизацию: каждый доступ к переменной —
это реальное чтение из памяти.

```c
static volatile bool rec_stop_flag;   /* Core 0 пишет, Core 1 читает */
static volatile bool rec_running;     /* Core 1 пишет, Core 0 читает */
```

Нужен ли мьютекс? Для простого флага типа `bool` — нет. На ARMv6-M (Cortex-M0+)
запись одного слова атомарна аппаратно: невозможно прочитать «половину» значения.
Мьютекс нужен только при модификации составных структур.

```c
/* Core 0: rec_stop_callback */
void rec_stop_callback(const char *args) {
    rec_stop_flag = true;    /* атомарная запись */
}

/* Core 1: в цикле записи */
while (!rec_stop_flag && ...) {
    /* ... */
}
```

Core 1 проверяет флаг между чанками. Максимальная задержка остановки ≈ 4 сек
(время DMA-чанка) + ≈ 3 сек (запись на SD). Это приемлемо для ручного управления.

### Исключение гонок на SD-карте

FatFS не потокобезопасна: если Core 0 и Core 1 одновременно делают `f_mount` /
`f_write` / `f_open` — структуры FAT в RAM будут испорчены.

Решение: пока `rec_running == true`, все SD-команды на Core 0 отклоняются:

```c
void sd_ls_callback(const char *args) {
    if (rec_is_running()) { printf("busy: recording in progress\n"); return; }
    /* ... */
}
```

`rec_is_running()` возвращает `rec_running` (volatile). Core 0 видит актуальное
значение, выставленное Core 1.

### Схема взаимодействия ядер

```
Core 0                          Core 1
──────────────────────────────  ──────────────────────────────────
rec_start_callback()
  rec_running = true
  multicore_launch_core1() ──→  core1_recording()
  return                           f_mount, f_open
                                   adc_init, dma_setup
командный цикл...                  loop:
                                     launch_dma(buf[next])
                                     write_chunk(buf[cur])
                                     wait_dma()
                                     if rec_stop_flag: break
rec_stop_callback()
  rec_stop_flag = true  ──────→  (видит флаг на след. итерации)
                                   выход из цикла
командный цикл...                  wav_fix_sizes (f_lseek)
                                   f_close, f_unmount
                                   rec_running = false  ──→  Core 0 видит
                                   return (Core 1 засыпает)
```

### Правила работы с двумя ядрами

1. **Никогда не обращайтесь к одному ресурсу с обоих ядер без синхронизации.**
   Примеры ресурсов: FatFS, структуры данных, периферия с состоянием (SPI).

2. **`volatile` — для флагов, мьютекс/спинлок — для составных структур.**
   `pico_sync` предоставляет `mutex_t` и `spin_lock_t`.

3. **`multicore_reset_core1()` перед повторным запуском.**
   Core 1 не «завершается» в обычном смысле — нужен явный сброс.

4. **Stacking: у каждого ядра свой стек.**
   По умолчанию Core 1 использует конец SCRATCH_X (4 KB). Для глубокой рекурсии
   или больших локальных переменных — нужно выделять явно.

5. **Периферия, которую инициализирует Core 1, доступна и Core 0** — и наоборот.
   Всё что нужно — не использовать одновременно.
